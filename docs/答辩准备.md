## 2. 演示主线（覆盖基础+进阶+AI 全部得分点）

1. 注册 → 登录（新账号）
2. 新建笔记（先私有）→ 上传配图 → 编辑
3. 设为公开 → 进入待审核
4. 切换 `admin / admin123` → 后台审核通过
5. 另一账号：浏览公开笔记 → 点赞/取消 → 评论/回复 → 关注作者
6. 看公开列表、关键词搜索、点赞排名、热门作者、关注动态
7. AI：总结 / 推荐 / 评分 → **手动确认保存**（强调不会自动改笔记）
8. AI 客服：新建会话 → 多轮追问（演示上下文理解）→ 切换历史会话
9. 后台：AI 调用统计次数变化、用户禁用/启用、下架笔记、删除评论

## 3. 数据库 11 张表速记卡

| 表 | 关键字段 | 设计理由（答辩口径） |
|---|---|---|
| `user` | role(USER/ADMIN)、status(1/0)、token_version | token_version 使改密后旧 JWT 全部失效，无需黑名单 |
| `note` | visibility(0私/1公)、audit_status(0待审/1过/2驳)、like_count、book_name | 审核状态机支撑"公开需审核"；like_count 冗余计数避免排行时联表 COUNT；书名存字符串（题目允许不建书表） |
| `note_image` | note_id、url、sort_order | 一对多配图，sort_order 控制展示顺序，逻辑删除 |
| `note_like` | uk(user_id, note_id) | 数据库唯一键兜底防重复点赞（并发下靠 DuplicateKeyException） |
| `follow` | follower_id / followee_id、uk 双列 | 唯一键防重复关注；两个方向的索引支撑"我的关注"和"粉丝列表" |
| `favorite_book` | uk(user_id, book_name) | 收藏书目，书名+用户唯一防重复收藏 |
| `comment` | parent_id 自关联、deleted | parent_id NULL=顶级评论；删除时 BFS 收集全部子孙**逻辑删除**，实现"父删子删" |
| `ai_log` | type、success(1/0)、prompt、response | 平台所有 AI 调用全量审计，支撑管理员统计（总/成功/失败）；私有笔记内容脱敏记录 |
| `note_ai` | uk(note_id)、type、content | 唯一键保证"一篇笔记只保存一种 AI 辅助结果"，覆盖式更新 |
| `conversation` | user_id、deleted | 会话归属唯一用户，越权访问返回业务异常 |
| `conversation_message` | role(user/assistant)、content | 消息按会话隔离持久化；删会话连带删消息 |

通用约定：InnoDB + utf8mb4、BIGINT 自增主键、蛇形命名、`created_at/updated_at` DATETIME、`deleted` 逻辑删除、不建外键约束（删除顺序灵活，关系在应用层维护）。

### 表关系口述脚本（30 秒版）

> 整个库以 user 和 note 为核心。user 对 note 一对多（visibility 区分私有公开、audit_status 承载审核状态机）；note 对 note_image 一对多（sort_order 控序）；user 和 note 通过 note_like 构成多对多（联合唯一键防重复点赞，like_count 冗余计数方便排名分页）；comment 自关联，parent_id 为空是顶级评论，父删除时应用层 BFS 找出全部子孙一起逻辑删除；note 对 note_ai 一对一（唯一键强制一篇笔记只存一种 AI 结果）；follow 是 user 自身的多对多（双向索引支撑粉丝列表和热门作者排名）；AI 侧 user 1—N conversation 1—N conversation_message，消息按会话隔离；所有 AI 调用统一写 ai_log 供管理员统计。全部表不建物理外键，关系在应用层维护；统一 InnoDB + utf8mb4 + 逻辑删除。

### 表设计演进的说法（应对"是不是一开始就设计好全部表"）

核心五张表（user/note/note_image/note_like/comment）先定；做管理员审核时给 note 加 audit_status；做 AI 时扩展出 ai_log/note_ai；做客服时加 conversation/conversation_message——随功能迭代逐步演进，符合"先基础后进阶"的设计思路。

## 4. 高频追问与答法

| 可能的问题 | 你的答法 |
|---|---|
| JWT 流程？ | 登录签发 HS256 token（含 userId/role/token_version）→ 拦截器解析 → 每次查库校验用户状态与 token_version（保证禁用/改密即时生效）→ ThreadLocal 存当前用户，afterCompletion 清理 |
| 密码怎么存？ | spring-security-crypto 的 BCryptPasswordEncoder，绝不明文 |
| 点赞如何防重？ | 先查后插 + 数据库唯一键兜底；like_count 用 `setSql("like_count = like_count + 1")` 原子自增，取消时 CASE 防负数 |
| 审核流程？ | 设为公开 → audit_status=0 进待审队列（对外不可见）→ 管理员 1 通过 / 2 驳回 → 用户修改内容后自动重新进入待审 |
| AI 结果怎么处理？ | 接口只返回结果，用户手动保存/丢弃；保存写入 note_ai 并覆盖旧结果，绝不自动改笔记主表 |
| 多轮对话 token 怎么控？ | 滑动窗口只取最近 20 条（10 轮），单条截断 500 字；用户与 AI 消息都持久化 |
| AI key 安全？ | 仅通过环境变量 AI_API_KEY 注入，仓库中只有占位符；未配置时返回 mock 结果，演示零依赖 |
| 文件上传安全？ | 后缀白名单 + 魔数校验 + 大小限制 + UUID 重命名 + 路径穿越防护 + 图片压缩 |
| 连接池？ | Spring Boot 默认 HikariCP |
| 异常处理？ | 自定义 BusinessException(code,msg) + @RestControllerAdvice 全局统一为 {code,message,data}；参数校验用 @Valid |
| 逻辑删除？ | MyBatis-Plus 全局配置 deleted 字段，查询自动过滤 |

## 7. 按《后端学习路线规划》对照：技术点 → 实现位置 → 一句话讲法

> 学习路线四个阶段即答辩考察清单；原话要求"能口述业务流程、数据库设计、分层架构、AI 业务约束"。

| 路线技术点 | 你的实现位置 | 一句话讲法 |
|---|---|---|
| Controller-Service-Mapper 三层职责 | `NoteController → NoteService → NoteMapper`（note/user/interaction/admin/ai 按功能分包） | Controller 只收参调 Service，Service 管业务/事务/权限，Mapper 只做 CRUD |
| 参数校验 | `NoteRequest` 的 @NotBlank/@Size + Controller @Valid | 校验在边界（DTO 注解），不合法直接 400 |
| yml 多环境配置 | `application.yml` + dev(H2)/prod(MySQL) 双 profile | 敏感配置全走环境变量，dev 零依赖可演示 |
| SLF4J 日志埋点 | 各 Service @Slf4j：登录、上传、AI 调用、审核等关键操作 | 登录/上传/AI 异常/重要业务操作都有 info/warn/error 日志 |
| 全局异常处理器 | `BusinessException` + `GlobalExceptionHandler`(@RestControllerAdvice) | 统一返回 {code,message,data}，校验/重复键/404/兜底 500 分开处理 |
| 请求链路 | 浏览器 → JwtInterceptor → Controller → Service → Mapper(MyBatis-Plus) → MySQL | 能顺着一条请求（如点赞）把链路讲一遍 |
| MultipartFile + 文件校验 | `NoteController.uploadImages`、`FileStorageService`（扩展名白名单+魔数+大小限制+UUID 重命名+压缩） | 不信任客户端：后缀会伪造，所以再验文件头魔数 |
| 本地存储 + DB 存 URL | uploads 目录 + `/api/images/{filename}` 映射；`note_image.url`、`user.avatar` 只存 URL | 数据库不存二进制，只存访问地址；多图用关联表 |
| JWT 原理 | `JwtUtil`（jjwt，HS256，claims: userId/role/ver） | 登录时签发、拦截器解析验签；token_version 让改密/禁用即时生效 |
| BCrypt | `UserService` + spring-security-crypto | BCrypt 自带盐且慢，防彩虹表；比对用 matches 不解密 |
| 拦截器 + ThreadLocal | `JwtInterceptor`/`AdminInterceptor` + `WebConfig` 注册 + `UserContext`(ThreadLocal) | 放行注册登录与匿名 GET 白名单；未登录 401，非管理员访问后台 403；afterCompletion 清理 ThreadLocal 防内存泄漏 |
| SpringAI + Prompt 设计 | `AiClient`（ChatClient，OpenAI 兼容）+ `AiService` 三个 systemPrompt | 每个功能专属 prompt；未配 key 走 mock 兜底，演示零依赖 |
| AI 异常处理 | `callAi` try/catch + error 日志 + ai_log 审计（成功/失败计数） | 失败返回友好提示，同时计入审计供管理员统计 |
| 交付物 | schema.sql、README、GitHub 公开仓库 | 自测完整跑一遍，能现场运行 |

**AI 编码考察口径（路线第 5 节）**：任指一个接口能讲清职能与三层流转；任指一个字段能讲含义；核心业务逻辑（点赞防重、审核状态机、AI 保存约束）脱离 AI 独立复述。

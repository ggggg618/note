# 笔记工坊 · 学习路线要求部分的原理详解

> 严格按《后端学习路线规划.pdf》要求的学习范围组织：前置基础 → JavaWeb/MySQL → Spring 四阶段 → AI → 交付。每节按"原理 → 我怎么实现 → 为什么这么设计"展开。

---

## 0. 前置基础（PDF 前言部分）

**前后端分离**：前端（HTML/CSS/JS）和后端（Java 接口服务）是两个独立程序，通过 **HTTP + JSON** 通信——前端发请求，后端返回 JSON 数据，前端自己渲染页面。本项目后端返回统一 `{code, message, data}`，前端 `app.js` 用 AJAX/fetch 调接口。

**Git 四个核心操作**：`pull` 同步远程 → `commit` 本地快照 → `push` 上传远程 → `reset` 回退版本。我的项目全程 Git 管理，提交记录按功能划分（如"图书库支持上传图片自动识别信息"），保证 AI 辅助写的每一步改动可追溯、可回退——这正是 PDF 强调的"AI 时代 Git 至关重要"。

**AI Coding 概念**：LLM 是概率生成模型；Token 是文本切分的最小单位，按量计费也占上下文；Context Window 是模型一次能"看到"的 token 上限（所以多轮对话要控制历史长度）；System Prompt 是给模型的角色/规则设定，User Prompt 是用户输入。我的 AI 客服就利用了这几个概念：System Prompt 限定客服只答平台问题，历史消息控制在窗口内防超限。

## 1. HTTP 与接口基础（PDF 二-1）

- **请求方法语义**：GET 查、POST 增、PUT 改、DELETE 删——我的接口严格 REST 语义（`POST /api/notes` 新建、`PUT /api/notes/{id}` 修改、`DELETE /api/notes/{id}` 删除）。
- **请求头**：`Authorization: Bearer <token>` 携带身份；`Content-Type: application/json` 与 `multipart/form-data`（传文件时）的区别——JSON 走 @RequestBody，文件走 MultipartFile。
- **响应码**：200 成功、400 参数错、401 未登录、403 无权限、404 不存在、500 服务器错。我的拦截器未登录返回 401，非管理员访问后台返回 403，全局异常按业务码映射。

## 2. MySQL 基础（PDF 二-3）

**事务 ACID**：
- **原子性**：一组 SQL 要么全成要么全不成。我的点赞是"插点赞记录 + like_count 加一"两步写，包在同一个 `@Transactional` 里，第二步失败第一步自动回滚，不会出现"记录有了计数没加"。
- **一致性/隔离性/持久性**：InnoDB 通过 undo/redo 日志和锁机制保证，应用层只需正确划定事务边界（只包写操作，不包长调用）。

**索引基础**：B+ 树结构，等值/范围查询从全表扫描降为树查找。我的建表原则：**外键列必建索引**（`note.user_id`、`note_image.note_id`），**查询条件列建索引**（`note(visibility, audit_status)` 组合索引支撑公开列表、`like_count` 支撑排名排序）。唯一索引（`note_like(user_id,note_id)`）同时承担防重约束。

**三范式与外键**：范式核心是"消除冗余、一个事实存一处"——点赞数本可以随时 COUNT 出来，但排名场景读多写少，我做了**受控冗余**（note.like_count），这是"范式服务于业务"的取舍，答辩能说出这个 trade-off 即可。外键我**逻辑上维护、物理上不建**：避免删数据时被约束顺序卡住，关系完整性由应用层事务保证。

**分页与分组**：物理分页 `LIMIT offset, size`（MyBatis-Plus Page 插件自动改写 SQL + 发 COUNT）；分组统计 `GROUP BY + COUNT`（热门作者按 followee_id 分组统计粉丝数）。

## 3. 数据库设计实战五点（PDF 二-数据库设计实战）

1. **用户与笔记一对多**：`note.user_id` 外键列 + 索引；私有/公开用 `visibility` 独立字段，不与审核状态混用——因为"私有不参与审核"，两个字段解耦后过滤条件清晰。
2. **笔记与图片一对多**：独立 `note_image` 关联表（`note_id` + `url` + `sort_order`），而不是 note 表里塞多列或逗号拼接——关联表才能按需增删单张图、维护顺序。
3. **点赞联合唯一**：`UNIQUE KEY(user_id, note_id)` 是**数据库层面**的防重，代码里先查后插只是友好提示，并发窗口靠唯一约束兜底（插重了抛 DuplicateKeyException，我捕获后转业务异常"请勿重复点赞"）。
4. **评论自关联 + 级联逻辑删除**：`parent_id` NULL 为顶级、非空指向父评论。父删子删不能用一条 SQL（层级任意深），我查出该笔记全部评论、按 parentId 建索引、**BFS 队列逐层收集全部子孙 id** 再统一逻辑删除（`deleted=1`）。逻辑删除的理由：可审计可恢复，MyBatis-Plus 查询自动过滤已删数据。
5. **ai_log 审计表**：每次 AI 调用记一条——`type`（哪种功能）、`prompt`（入参）、`response`（原始返回）、`success`(1/0)、`created_at`（时间）。管理员统计就是对这个表 `COUNT + GROUP BY success`，天然区分成功失败。

**表关系口述**：user 1—N note 1—N note_image；user N—M note（经 note_like）；note 1—N comment（自关联）；note 1—1 note_ai；user N—M user（经 follow）；user 1—N conversation 1—N conversation_message；所有 AI 调用 → ai_log。

## 4. 阶段一：SpringBoot + MyBatis-Plus 分层（PDF 三-阶段一）

**三层职责（为什么要分层）**：
- **Controller**：只做"接请求、调 Service、返结果"。它不写业务，所以同一业务能同时被页面接口和测试复用，且 Controller 不碰 Mapper——业务规则收敛在 Service 一处。
- **Service**：业务逻辑、权限判断、事务边界。多步写操作（点赞两步写、删笔记连带删图/赞/评论）都在这里加 `@Transactional`。
- **Mapper**：只做 CRUD，继承 MyBatis-Plus `BaseMapper`，通用增删改查零 SQL，复杂查询用 LambdaQueryWrapper 拼条件。

**请求链路（PDF 要求能讲整条）**：浏览器发 HTTP → `JwtInterceptor` 验 token 放行 → Controller 接参（`@PathVariable/@RequestParam/@RequestBody/@Valid`）→ Service 业务处理 → Mapper 执行 SQL → MySQL → 数据原路返回，Controller 包装成 `{code,message,data}`。

**yml 配置**：SpringBoot 约定大于配置，`application.yml` 集中管理；我用 `spring.profiles.active` 区分 dev（H2 内存库，零依赖演示）/ prod（MySQL），敏感项全走 `${环境变量:默认值}` 占位符。

**SLF4J 日志**：门面模式——代码面向 SLF4J 接口，底层实现是 Logback。PDF 要求的"关键操作埋点"我都有：登录成功/失败（info/warn）、文件保存成功/失败、AI 调用异常（error 带堆栈）、管理员审核/下架。原则：**对外信息最少，对内日志最全**。

**全局异常处理器**：`@RestControllerAdvice` 是切面，捕获所有 Controller 抛出的异常。我自定义 `BusinessException(code, message)`，业务失败直接 `throw new BusinessException("笔记不存在")`，处理器统一转成 `{code,message,data}`；`@Valid` 校验失败捕获 `MethodArgumentNotValidException` 拼字段错误；兜底 Exception 记 error 堆栈但只对外返回"Internal server error"——**堆栈不外泄**。好处：业务代码零 try-catch 噪音，错误格式全站一致。

## 5. 阶段二：文件上传（PDF 三-阶段二）

**上传原理**：前端 `form-data` 编码文件 → Spring 用 `MultipartFile` 接收（内部是临时文件流）→ 服务端决定存哪里 → 数据库记访问 URL。

**校验为什么不能只看后缀**：后缀由客户端控制，改成 .jpg 的可能是任何文件。我的校验链（`FileStorageService`）：
1. 非空；
2. 扩展名白名单（jpg/jpeg/png/gif/webp）；
3. 大小限制（图 10MB）；
4. **魔数校验**——读文件头字节比对：JPEG `FF D8 FF`、PNG `89 50 4E 47`、GIF `GIF8`、WebP `RIFF..WEBP`。文件头是格式规范强制的，伪装文件过不了这关；
5. UUID 重命名——丢弃用户原始文件名，防 `../` 路径穿越与重名覆盖，读取时再 `normalize + startsWith(root)` 双保险。

**本地存储方案**：文件存 `uploads/` 目录，通过 `/api/images/{filename}` 接口映射访问（按后缀返回 Content-Type）；数据库只存 `/uploads/xxx.png` 这样的 URL 字符串——**二进制不入库**，数据库只存指针，这也是 PDF 原话要求。

**多图关联表**：一张笔记多张配图 = note_image 表多行，`sort_order` 控制展示顺序；上传/删除单张图互不影响。

## 6. 阶段三：JWT + BCrypt + 拦截器（PDF 三-阶段三）

**JWT 原理（token 组成 → 签名 → 生成 → 解析）**：
- **组成**：`Header.Payload.Signature` 三段 Base64。Header 声明算法（HS256）；Payload 放 claims（我的：userId、username、role、签发时间、过期时间）；Signature = HMAC-SHA256(前两段, 服务端密钥)。
- **为什么伪造不了**：Base64 只是编码不是加密，任何人都能解开看 Payload——但**改了内容签名就对不上**，服务端用密钥重算签名比对即可识破。安全性全部来自**密钥不泄露**（我的密钥走 JWT_SECRET 环境变量，长度不足 32 启动直接报错）。
- **什么时候生成**：登录/注册成功时（密码比对通过后）。
- **怎么解析**：`jjwt` 的 parser 验签 + 验过期，通过后取出 claims。
- **trade-off（加分表述）**：JWT 无状态，服务端不存会话，横向扩展友好；代价是签发后到过期前始终有效，无法主动作废——所以登出/禁用是这类方案的固有弱点，可用短时效 + 服务端状态校验缓解。

**BCrypt（为什么不能明文）**：数据库泄露时明文密码直接暴露，且用户多处复用密码危害放大。BCrypt = **随机盐 + 慢哈希**：盐嵌在结果串里（`$2a$10$...`，10 是 cost 因子），相同密码每次哈希结果都不同 → 彩虹表失效；故意算得慢 → 暴力枚举成本指数上升（MD5 微秒级算几十亿次，BCrypt 只能几百次）。**加密用 `encode()`，比对用 `matches(明文, 库中哈希)`——取出盐重算再比，没有"解密"**。

**拦截器（Interceptor）**：
- **注册**：`WebConfig implements WebMvcConfigurer`，`addInterceptors` 注册 JwtInterceptor 拦 `/api/**` 放行注册/登录，AdminInterceptor 拦 `/api/admin/**`。
- **执行时机**：`preHandle` 在 Controller 之前——鉴权就发生在这里：无 token 且非放行路径 → 直接写回 401 JSON 并返回 false（请求到此结束）；token 无效 → 401。
- **角色校验**：AdminInterceptor 检查 `UserContext` 里的 role，非 ADMIN 返回 403——**普通用户摸不到管理员接口**。
- **ThreadLocal 存当前用户**：验证通过后把 AuthUser 放进 `ThreadLocal`，后续 Controller/Service 用 `UserContext.id()` 取，不用层层传参、不耦合 request 对象。**关键在清理**：Tomcat 线程池复用线程，不清理会让下一个请求读到上一个用户——所以我在 `afterCompletion` 里 `UserContext.clear()`，这个回调在 Controller 抛异常时也保证执行。
- **放行配置**：注册、登录不拦；公开浏览类 GET 接口匿名放行（未登录也能看公开笔记），但 Service 层对"非公开内容"仍有权限判断——拦截器管"进不进来"，Service 管"能看哪条"。

## 7. 阶段四：Spring AI（PDF 三-阶段四）

**跑通调用**：引入 `spring-ai-starter-model-openai` 依赖，yml 里配 `api-key / base-url / model`（全部 `${环境变量:占位符}` 注入，**PDF 加粗提醒：api-key 绝不入仓库**）。调用就三步：`ChatClient.prompt().system(角色设定).user(输入).call().content()`——拿到模型返回的纯文本。

**Prompt 设计（三个功能各一个专属 System Prompt）**：
- 总结："生成简洁清晰的内容摘要"；
- 推荐："推导适宜人群并说明理由"；
- 评分："从完整性、相关性、思考深度三维度打 0-100 分并说明依据"。
System Prompt 定角色和输出要求，User Prompt 传笔记正文——**把格式约束写进 System，输出才稳定**。

**业务流程约束**：接口只返回 AI 结果 → 前端展示 → 用户手动点保存才写入 `note_ai`（唯一键保证一篇笔记只存一种）→ 永不自动修改笔记主表。这是"AI 辅助而非替代"的产品约束，也是 PDF 的业务要求。

**异常处理（PDF 明确要求）**：AI 调用包在 try-catch 里——捕获后记 **error 日志**、写入 ai_log 失败记录（与统计打通）、对用户返回友好提示"AI 调用失败"，绝不把底层异常堆栈抛给前端。另外 key 未配置时返回模拟结果，本地演示零依赖。
